対象: ZIP 内 `crew-ascent/` 全21ページ

## 0. まず、前回の修正が効かなかった理由

前回は「読み込むCSSが違う」「画像の先読み関数が呼ばれていない」まで突き止めましたが、
**それだけでは足りませんでした。** 今回ブラウザのトレースを取って、はっきりしました。

前回の修正で消えなかった、もっと大きな停止が2つ残っていました。

| ページ | 最悪の1コマ（前回修正後・初回訪問時） |
|---|---|
| services.html | **159ms** — SVG図版の読み込み・解析・レイアウト |
| plans.html | **27ms** ×10回 — 画像の展開（デコード） |

**159ms は、60fps なら約9コマ連続の停止です。**
スクロールは時間で進むので、9コマ止まったあとに描けた画面は
その分まとめて進んだ位置になります。これが「加速」の正体でした。

さらに、修正版のCSS/JSがブラウザに届いていなかった可能性もあります
（ファイル名に版番号が無いため、古い `base.css` / `top.js` が使われ続ける）。
今回はそこも塞ぎました。

## 2. 原因（実測で確定した順）

### 原因1【最大・159ms】SVG図版を `<img>` で置いていた

`services.html` と `website-guide.html` の図版は `<img src="....svg">` でした。

Chrome は `<img>` のSVGを**独立したSVG文書**として扱います。つまり

1. スクロールで近づいてはじめて取得が始まる（`loading="lazy"`）
2. 届いた瞬間に XML を解析し、SVG用の文書を作り、
3. その文書のレイアウトを実行し、
4. **中の日本語テキスト30件を組み直す**

これが1コマの中で全部起きます。トレース上の内訳:

```
ResponseBodyLoader::DidFinishLoadingBody   159.2ms
  ImageResourceContent::updateImage        150.0ms
    SVGImage::DataChanged                  148.9ms
      IsolatedSVGDocumentHost              148.9ms
        XMLDocumentParser::end             140.4ms
          Document::UpdateStyleAndLayout   137.2ms   ← レイアウト
PaintImage  service-scope-map.svg           77.1ms   ← しかも描くたびに再実行
```

さらに `PaintImage 77.1ms` — **ラスタ化のたびに30件の日本語テキストを組み直します。**
一度きりではなく、その図版が画面に入るたびに起きていました。

**修正**: 2枚のSVGを**HTMLに直接書き込み**ました（インラインSVG）。
本文の一部になるので、組み版は読み込み時の1回だけ。見た目は完全に同じです。
→ services.html の最悪コマ **159.2ms → 6.8ms**

### 原因2【大・最大39ms】`loading="lazy"` が展開をスクロール中に持ち込んでいた

29枚の画像すべてに `loading="lazy"` が付いていました。lazy は
「画面に入る直前に取得 → その場で展開」なので、**取得も展開もスクロール中**に走ります。
1枚あたり 15〜39ms。連続スクロールでは、これが画像のたびに積み上がります。

**修正**: `loading="lazy"` を全廃し、代わりに
- 各ページ先頭以外の画像へ `fetchpriority="low"`（最初の表示と取り合わない）
- `decoding="async"` は維持

これで取得も展開も**読み込み時**に移ります。JavaScript が無効でも効きます。

### 原因3【中・最大27ms】画像が表示サイズの4〜5倍あった

図版は 1800×1000 = 180万画素ですが、実際に表示されるのは
デスクトップで約 864px、スマホで約 359px 幅です。
**展開の費用は元画像の画素数に比例する**ので、必要の4〜5倍払っていました。

元のHTMLには `sizes="(min-width: 900px) 60vw, 92vw"` が書かれていましたが、
**`srcset` が無いため、この指定は一度も働いていませんでした**（書きかけのまま）。

**修正**: 20枚の縮小版を生成し、`srcset` + `sizes` を正しく組みました。

| 画像 | 元 | 追加した縮小版 |
|---|---|---|
| 図版8枚 | 1800×1000 | 900×500 |
| ph-four-views / ph-color-in-dark | 1600×686 | 800×343 |
| ph-four-areas | 1448×620 | 724×310 |
| hero-light | 1438×809 | 760×428 |
| band 3枚 | 1800×288〜375 | 900×144〜188 |
| ph-appr 3枚 / ph-drawing-grid | 1100×471 | 560×240 |

1倍デスクトップとスマホは 900px 版を、高精細ディスプレイは元画像を選びます。
実測で 1440px の画面が 864px 相当を選ぶことを確認済みです。

### 原因4【中】前回修正ぶん（再掲・すべて維持しています）

- 固定ヘッダーの `backdrop-filter`（下層20ページで常時。写真や濃色面の上で特に重い）
- `predecodeImages()` が `init()` から呼ばれていなかった（デッドコード）
- 濃色の章に方眼が二重に掛かっていた
- `.glist a:hover` が `padding-left` を動かし、スクロール中に連続でレイアウトを走らせていた
- 対策が `top.css` にしか無く、下層20ページに届いていなかった

### 原因5【配布事故】CSS/JS に版番号が無かった

`<link href="assets/css/base.css">` のように版番号が無いため、
一度開いたブラウザは**古いCSS/JSを使い続けます**。
修正を配っても反映されない状態でした。

**修正**: 全110か所へ `?v=20260817b` を付けました。

## 2. 原因: 大きな写真の上に半透明が二枚重なっていた

切り分けのため、層を一つずつ外して計測しました。

| 外したもの | 濃色区間の p95 |
|---|---|
| `.sec--ink::before`（方眼） | 33.3ms（変わらず） |
| **画像の `opacity` を 1 に** | **16.7ms** |
| **`::after` のグラデを外す** | **16.7ms** |
| `contain: paint` を外す | 33.3ms（**悪化**。この指定は効いているので残す） |

つまり **「半透明の画像」と「半透明のグラデ」が二枚重なっている**ことが原因でした。

```css
.pband--ink img  { opacity:.62; }   /* ← 画像1枚ぶんの透明レイヤを作る */
.pband--ink::after { background:linear-gradient(...); }  /* ← その上にもう一枚 */
```

画像に `opacity` を掛けると、その大きさぶんの透明レイヤを作って合成し直すことになります。
そこへさらにグラデを重ねるため、**大きい写真＝濃色の帯**でだけ費用が跳ね上がっていました。

## 3. 修正: 二枚を一枚に合成（見え方は同じ）

地色はどれも `#14161A` なので、二枚は数式で一枚にまとめられます。

> 合成後の不透明度 **a = a₁ + a₂ − a₁·a₂**

| 対象 | 修正前 | 修正後 |
|---|---|---|
| `.pband--ink` | `img opacity:.62` + グラデ(1 / .15 / 1) | `img opacity:1` + グラデ(1 / **.473** / 1) |
| `.roles__ph` | `img opacity:.20` + グラデ(.55 / 1) | `img opacity:1` + グラデ(**.91** / 1) |
| `.band-photo` | `img opacity:.45` + グラデ(.62 / .28 / 1) | `img opacity:1` + グラデ(**.829 / .676** / 1) |

**見え方が変わっていないことをピクセル単位で確認しました。**

| 対象 | 最大の色差（255段階） | 4/255を超えた画素 |
|---|---|---|
| `.pband--ink` | 2 | 0.00% |
| `.roles`（写真＋文字） | 14 | 0.01% |
| ヒーロー | **0** | 0.00% |

（ヒーローは重ね順が変わるため統合を取りやめ、完全に元のままにしました。）

ここから先は、**この環境（ヘッドレス・ソフトウェア描画・共有マシン）の測定限界**です。
方眼の重ね塗りを外しても差が出ず、DPR 2 でも差が出ませんでした。

1. **環境固有の要因** — GPUドライバ、ブラウザの「スムーズスクロール」設定、

キャプションの帯を常に画面内へ残す）と改善します。これは見た目の変更になるため、

# 第4版 — 根本原因（これまでの3回が外していたもの）

## 0. 方向転換の決め手

**Chrome / Safari / Edge のすべてで同じように起きる** というご報告が決定打でした。

Chrome と Edge は Blink、Safari は WebKit で、**描画エンジンが違います**。
描画が間に合わないことが原因なら、エンジンごとに出方が変わるはずです。
3つで一致するなら、原因は描画ではなく **版面（レイアウト）の構造**にあります。

第1〜3版で直したのは、すべて「描画を速くする」対策でした。
実際に速くはなりましたが（services.html の 159ms → 6.8ms など、これらは本物の不具合です）、
**体感が変わらなかったのは、測る対象そのものが違っていたから**です。

## 1. 根本原因: 動きの基準になるものが画面から消える区間が長すぎた

ページ全体を10px刻みで走査し、**見出し・本文・箇条書き・表・キャプション・ボタン・罫が
1つも存在しない縦の区間**を測りました（1440×900）。

| 区間 | 長さ | 画面比 | 該当 |
|---|---|---|---|
| y=5790→6340 | **550px** | **61%** | `ph-four-areas`（ご指摘の写真2枚目） |
| y=10220→10750 | **530px** | **59%** | band-opening |
| y=2300→2820 | **520px** | **58%** | `ph-four-views`（1枚目） |
| y=4760→5280 | **520px** | **58%** | `ph-color-in-dark`（3枚目） |
| y=8200→8720 | **520px** | **58%** | band-shop-morning→Perspective（4枚目） |

**いただいた4枚のスクリーンショットが、そのまま上位5件に入っています。**

画面の**6割が均一な写真や濃色面だけ**になると、目の位置の手がかりが無くなります。
速度が同じでも速く動いて見えます。これは

- **エンジンに依存しません**（Chrome / Safari / Edge で同じ ← ご報告と一致）
- 画像と濃色面でだけ起きます（そこだけ目印が消えるため）
- **止めれば起きません**（止まれば区間の端が見え、位置が分かる）

### 裏づけ: スマホでは起きない構造だった

同じ計測を 390×844 で行うと、**修正前でも最大 170px（画面の20%）**しかありません。
スマホでは図版が 149px（画面の18%）にしかならないためです。

**描画性能が原因なら、CPUの弱いスマホほど悪化するはずです。**
逆にデスクトップでだけ起きるという事実が、原因が「描画」ではなく
「画面に対する図版の大きさ」であることを示しています。

## 2. 修正

写真は残します。**高さだけを詰め、本文とキャプションが必ず同時に見える**ようにしました。

```css
/* 図版の写真: 画面の4割まで */
.fig--photo img { max-height: min(40vh, 360px); object-fit: cover; }

/* 章と章のあいだの写真帯 */
.pband--sm  { height: clamp(120px, 13vw, 180px); }   /* 260px → 180px */
.pband--md  { height: clamp(150px, 17vw, 240px); }   /* 360px → 240px */
.band-photo { height: clamp(110px, 13vw, 170px); }   /* 230px → 170px */

/* 帯の前後は章の余白がそのまま無地の区間に足される。
   実測で 帯240px に対し 前94px + 後77px が付いていた。接する側だけ詰める。 */
.pband + .sec       { padding-block-start: clamp(28px, 2.6vw, 44px); }
.sec:has(+ .pband)  { padding-block-end:   clamp(28px, 2.6vw, 44px); }
```

## 3. 修正後の実測（1440×900）

|---|---|---|
| `ph-four-views`（1枚目） | 520px / 58% | **350px / 39%** |
| `ph-color-in-dark`（3枚目） | 520px / 58% | **350px / 39%** |
| `ph-four-areas`（2枚目） | 550px / 61% | **320px / 36%** |

# 第6版 — 「トラックパッドで起き、タッチで起きない」から原因が確定

## 0. この一言が決定的でした

> トラックパッド問題あり、画面タッチ問題なし

この2つの決定的な違いは **ホバー（`:hover`）** です。

- **トラックパッド／マウス** … ポインタは画面上の一点に留まったまま、
  その下を **カード・ボタン・リンク・36マスが次々に通過する**。
  つまり **スクロール中ずっとホバーが連続発火する**。
- **画面タッチ** … ホバーそのものが存在しない。

そして **私のこれまでの計測は、一度もホバーを発生させていませんでした。**
ブラウザに合成スクロールを送っていただけで、ポインタを本文の上に置いていなかったためです。
5回外し続けた理由がこれです。

## 1. 実測（1440×900・CPU4倍遅い設定・同じ距離・ポインタは本文の上 x=720・各3回）

| | スタイル再計算 | **レイアウト** | 長いコマ>20ms |
|---|---|---|---|
| ホバーが効く状態（元の挙動） | 162〜164 | **9〜10** | **6〜7** |
| スクロール中ホバーを止めた状態 | 138〜139 | **1** | **3〜4** |

**レイアウトが 9〜10回 → 1回。** 3回とも同じ結果でした。

さらに、ポインタの位置を変えるだけで差が出ます（対策前）。

| ポインタ位置 | レイアウト | 長いコマ>20ms |
|---|---|---|
| 左端の余白（ホバーしない） | 4 | **7** |
| 本文の上（ホバー発生） | 9 | **15** |

**ポインタが本文の上にあるだけで、落ちるコマが倍**になります。

## 2. 何が重かったか

スクロール中に通過するたび、190msのトランジション付きで次が走っていました。

| 指定 | 内容 |
|---|---|
| `.glist a:hover .glist__th img` | `transform: scale(1.05)` — **画像を拡大** |
| `.tmap__c:hover` | `filter: brightness(.92)` — **36マスそれぞれ** |
| `.btn--primary:hover` | `box-shadow: 0 12px 34px` — **大きなぼかし影** |
| `.pcard:hover` / `.appr__tab:hover` | 背景色（大きなカード4枚） |
| `.ftr a:hover` / `.breadcrumb a:hover` ほか | `text-decoration: underline` — **これがレイアウトを起こす** |

190msのトランジションは、次の要素が通過する前に終わらないので **重なり続けます**。

## 3. 対策

スクロールしている間だけ、当たり判定（ホバー）を止めます。

```css
html.is-scrolling,
html.is-scrolling * { pointer-events: none !important; }
```

```js
/* 既存のスクロール購読口に相乗り。最後のスクロールから120msで元に戻す */
function suspendHover() {
  if (hoverTimer === null) root.classList.add('is-scrolling');
  else clearTimeout(hoverTimer);
  hoverTimer = setTimeout(function () {
    hoverTimer = null; root.classList.remove('is-scrolling');
  }, 120);
}
```

見た目は一切変わりません。止まればホバーは元どおり効きます。

### 壊れていないことの確認

| 項目 | 結果 |
|---|---|
| スクロール中にクラスが付く | ○（1回だけ付与。付け外しを繰り返さない） |
| 停止後にクラスが外れる | ○ |
| スクロール中のボタン `pointer-events` | `none`（＝止まっている） |
| 停止後のボタン `pointer-events` | `auto`（＝戻っている） |
| 停止後のリンククリック | ○ 遷移する |
| ナビのホバー展開 | ○ 効く |
| JSエラー | なし |

### 節ごとの効果（実ポインタを本文の上に置いて計測）

| 区間 | 対策なし | 対策あり |
|---|---|---|
| **guides（読み物一覧）** | **p95 33.4ms / 落ち4回** | **16.7ms / 0回** |
| plans（カード4枚） | 16.7ms / 0回 | 16.7ms / 0回 |
| report（濃色） | 16.8ms / 0回 | 16.7ms / 0回 |

`.glist a:hover` で画像を拡大している読み物一覧で、いちばんはっきり効きました。

## 4. もう一つのトラックパッド固有の事情（これまでの修正が効く理由）

トラックパッド／マウスの **ホイール入力は、ブラウザが滑らかに見せるための
アニメーションを挟みます**。コマが落ちると、そのぶんを次のコマでまとめて進むため、
**同じ量のカクつきでも「加速」として見えます**。

一方 **タッチのフリックは合成スレッドが直接動かす**ので、
本体側が詰まっていても滑らかなままです。

つまり **同じカクつきでも、トラックパッドでだけ「加速」に化ける**ということです。
第1〜5版で削ったカクつき（SVGの159ms停止、スクロール中の画像展開、
下層20ページに届いていなかった対策など）は、すべてこの経路で効きます。
戻す理由はありません。

## 5. 正直にお伝えすること

- ホバーの件は **3回とも同じ結果が出た再現性のある発見**で、
  「トラックパッドで起きてタッチで起きない」を初めて説明できる原因です。
- ただし、写真の帯や濃色面の区間は、計測のばらつきの範囲内で
  はっきりした差が出ていません。そこは引き続き未確定です。
- 今回もまだ変わらない場合は、`?diag=1` の
  **「A. 入力量 vs 実移動量」の比**を教えてください。
  1.00前後なら原因はサイトの外（ブラウザ／OSの慣性）、
  1.15以上ならサイト側です。ここがまだ埋まっていません。

# 第7版 — 「修正可能ですか？」への回答: 可能です

## 1. 「加速」を数値で捉えました

ホイール入力の勢いを変えて、**最高速度**を測りました（1440×900）。

| 操作の勢い | 標準スクロール | 速度固定あり |
|---|---|---|
| ゆっくり | 3,614 px/秒 | 1,317 px/秒（比1.00） |
| やや速い | 7,229 px/秒 | 2,575 px/秒（比1.00） |
| **勢いよく** | **25,301 px/秒** | **2,590 px/秒**（比0.46） |

**標準では、操作の勢いに応じて最高速度が 3,614 → 25,301 px/秒 と7倍に跳ね上がります。**
これがOSとブラウザが掛ける「慣性」で、**サイトのCSS/HTMLからは制御できません。**

速度固定を入れると 1,317 → 2,590 px/秒、**2倍以内**に収まります。

## 2. 対策: `assets/js/scroll-steady.js`

ホイール入力を引き取り、自前で動かします。
**普段の操作（ゆっくり／やや速い）は比1.00で素通し**、暴走だけを抑えます。

### 使い方

| したいこと | 方法 |
|---|---|
| **今すぐ試す** | URLの末尾に **`?steady=1`** |
| 標準に戻して比べる | URLの末尾に **`?steady=0`** |
| **常時オンにする** | `assets/js/site-config.js` に `steadyScroll: true,` を1行足す |

### 重さ・軽さの調整（`site-config.js`）

| 設定 | 既定 | 意味 |
|---|---|---|
| `steadyStepCap` | 120 | 1イベントで受け付ける最大px。小さいほど勢いを切り捨てる |
| `steadySpeedCap` | 60 | 1コマの上限px（60 = 毎秒3600px）。小さいほど最高速度が下がる |
| `steadyEase` | 0.26 | 大きいほど機敏、小さいほど滑らか |

### 壊れていないことの確認

| 項目 | 結果 |
|---|---|
| PageDown / End キー | ○ 横取りしない |
| ページ内リンク（`#plans`） | ○ 効く |
| リンクのクリック遷移 | ○ |
| ドロワー（入れ子のスクロール領域） | ○ 横取りしない・背面ロックも動作 |
| `?steady=0` で標準へ復帰 | ○ 400px入力 → 400px移動 |
| `prefers-reduced-motion` | ○ 補間せず即座に移動 |
| タッチ（画面タッチ） | 対象外。ブラウザ標準のまま |
| JSエラー | なし |

## 3. 「修正可能か」の整理

| 層 | 状態 |
|---|---|
| サイト側の実在の不具合（SVGの159ms停止、スクロール中の画像展開、下層20ページに対策が届いていなかった件、ホバーの連続発火） | **修正済み。実測で確認** |
| ブラウザ／OSがホイールに掛ける慣性 | CSS/HTMLでは**制御不可**。ただし **JSで引き取れば速度を固定できる**（本版） |
| 画面タッチ | 元から問題なし（ホバーが無く、フリックは合成スレッドが直接動かすため） |

**つまり「加速しない」状態は確実に作れます。** `?steady=1` で今すぐ確認できます。

これで直ったら `site-config.js` に1行足して常時オンにしてください。
既定でオンにしていないのは、ブラウザ標準のスクロールを上書きする方式であり、
採用するかどうかはご判断いただく事項だからです。
